# 008 · 사주 해석 결과 이력 저장

## 목적

로그인한 사용자가 Gemini로 생성한 사주 해석을 자신의 데이터베이스 이력으로 쌓고, 같은 계정으로 다시 로그인했을 때 이전 결과를 안전하게 볼 수 있게 합니다.

## 확정한 범위와 선행 조건

- 참가자 선택: **결과를 생성할 때마다 모두 저장**하고 이전 결과 목록을 제공합니다. 최근 1건으로 덮어쓰지 않습니다.
- Spec 007의 Google 로그인과 서버 인증이 선행 조건입니다. 로그인하지 않은 사람의 결과는 데이터베이스에 저장하지 않습니다.
- 기존 `localStorage`의 익명 결과를 어느 계정에도 자동 이관하지 않습니다. 데이터베이스를 로그인 사용자 결과의 기준 저장소로 삼습니다.

## 저장 자료

`saju_readings` 테이블을 계획합니다. 실제 프로젝트에 같은 이름의 테이블이나 정책이 있는지 구현 전에 확인합니다.

| 필드 | 뜻 |
|---|---|
| `id` | 결과 식별용 UUID, 기본키 |
| `user_id` | Supabase Auth 사용자 ID, `auth.users` 참조 |
| `chart` | 서버에서 계산한 네 기둥·오행·일간 등 화면 표시용 결과(JSON) |
| `reading` | 서버에서 검증한 Gemini 해석과 네 분야 조언(JSON) |
| `model` | 생성에 사용한 모델 ID (`gemini-3.5-flash-lite`) |
| `schema_version` | 저장 형식 버전 |
| `created_at` | 서버가 정한 생성 시각 |

- 생년월일·출생시간 **원문**, Gemini API 키, Google 토큰·Client Secret, 사용자 이메일은 이 테이블에 저장하지 않습니다. 계산된 `chart`도 개인에 관한 정보이므로 보호 대상입니다.
- 화면의 연도별 흐름과 관계 유형은 저장된 `chart`에서 다시 계산합니다. 해당 연도의 기준이 바뀔 수 있으므로 생성 당시 안내와 현재 재계산 안내를 구분합니다.

## 사용자 흐름과 실패 처리

1. 로그인한 사용자가 해석을 요청하면 서버가 입력·세션을 검증하고 사주 계산과 Gemini 해석을 마친 뒤, **검증된 결과만** 로그인 사용자 ID로 삽입합니다. 클라이언트가 보낸 `user_id`나 해석 본문을 저장 근거로 쓰지 않습니다.
2. 저장에 성공하면 결과 화면에 저장 완료를 표시합니다. 별도의 `/history` 화면에서 이력 목록을 최신순으로 불러오며, 페이지 단위로 나누어 오래된 결과도 볼 수 있게 합니다. 항목을 고르면 생성 시각과 해석을 다시 볼 수 있습니다.
3. 사용자는 자신의 결과 한 건을 삭제할 수 있습니다. 삭제 전 대상과 복구 불가 여부를 확인하고, 성공 후 목록에서 제거합니다. 다른 사람의 결과는 조회·삭제할 수 없습니다.
4. Gemini 생성은 성공했지만 데이터베이스 저장이 실패하면 현재 화면의 해석을 보여주되 **저장되지 않음**을 분명히 알립니다. 저장됐다고 표시하거나 조용히 브라우저 결과를 서버 이력으로 가장하지 않습니다. 새로고침 후 복원되지 않을 수 있음을 알려줍니다.
5. 목록·상세 조회 실패에는 기존 화면을 유지하고 재시도 수단을 제공합니다. 중복 제출과 네트워크 재시도로 같은 결과가 여러 번 저장되지 않도록 요청 식별자 또는 동등한 중복 방지 수단을 둡니다.

## 접근 통제와 보존

- 테이블에 행 단위 보안 정책(RLS: 데이터베이스가 요청자별로 볼 수 있는 행을 제한하는 규칙)을 켜고, 로그인 사용자의 `auth.uid() = user_id`인 행에만 `SELECT`, `INSERT`, `DELETE`를 허용합니다. `UPDATE`는 이번 범위에서 허용하지 않습니다. 익명 사용자는 어떤 행도 볼 수 없습니다.
- 서버에서도 매 요청마다 현재 사용자를 검증합니다. 서비스 역할 키로 RLS를 우회해 사용자의 결과를 읽고 쓰는 방식은 사용하지 않습니다.
- `user_id`에는 조회를 위한 인덱스를 두고, 목록은 최신순·페이지 단위로 조회합니다. 사용자가 직접 지우지 않은 이력의 자동 만료는 이번 범위에 두지 않습니다. 계정 삭제 시 관련 행이 어떻게 처리되는지 구현 전에 명시적으로 확인합니다.
- 데이터베이스 변경은 버전이 남는 마이그레이션 파일로 관리하고, 운영 프로젝트에 바로 적용하기 전에 검토·백업합니다. 현재 MCP 연결은 읽기 권한으로 인증되어 있으므로 Spec 작성 과정에서 테이블을 생성하거나 수정하지 않습니다.

## 확인 기준

- 로그인한 A의 결과를 여러 번 생성하면 각 결과가 별도 행으로 남고, 최신순 목록·상세 조회·한 건 삭제가 동작합니다.
- B나 익명 사용자가 A의 ID를 추측하거나 요청의 `user_id`를 바꿔도 A의 행을 조회·삽입·삭제할 수 없습니다. 데이터베이스 정책 시험으로도 검증합니다.
- 잘못된 입력, Gemini 실패·불완전한 응답, 로그인 만료 시 새 행이 생기지 않습니다. DB 실패 시 성공한 척하지 않습니다.
- 새로고침·다른 기기에서 같은 계정으로 로그인하면 저장 이력이 보입니다. 다른 계정으로 전환하면 이전 계정 데이터가 화면에 남지 않습니다.
- 원본 출생일시와 비밀값이 저장 행·브라우저 공개 파일·로그에 포함되지 않습니다. 기존 사주 계산·오행·흐름·관계 화면도 통과합니다.

## 제외할 것

- 다른 사람과 결과 공유, 관리자 열람 화면, 이력 검색·태그, 익명 결과 자동 이관, 결제·유료 상담.

## 검증 기록

- 2026-09-23: 사용자별 전체 결과를 위한 마이그레이션 파일, 저장·최신순 페이지 목록·한 건 삭제 API, 화면의 이력 선택·삭제·미저장 안내를 구현했습니다. 기존 브라우저 결과는 자동 이관하지 않습니다.
- 전체 자동 시험 46개, TypeScript 검사, 배포용 빌드가 통과했습니다. 익명 상태의 이력 목록·삭제 API는 401을 반환했습니다. 마이그레이션 시험은 SQL의 구조적 안전장치만 검사하며 실제 데이터베이스의 행 단위 보안 동작을 증명하지 않습니다.
- 현재 연결된 Supabase 프로젝트에서 `saju_readings`가 없는 것(REST 조회 404)을 확인했습니다. 마이그레이션은 아직 적용하지 않았고, 실제 계정 A/B 분리·저장·조회·삭제 시험도 남아 있습니다. 완료 체크는 보류합니다.
- 이후 2026-09-23 재확인에서는 같은 프로젝트의 `saju_readings`가 존재했습니다. 익명 REST 조회는 권한 오류 401을 반환했고, 로그인된 앱에서 생성된 결과가 `계정에 저장됨`으로 표시되며 `/history` 목록에도 나타났습니다. 이 확인 과정에서 Codex는 SQL을 실행하지 않았으므로 누가 언제 테이블을 만든 것인지는 확인되지 않았습니다. 계정 A/B 분리와 실제 정책 정의는 아직 시험하지 않았습니다.
